Nuestro diseño

Cómo modelamos el problema

Cada persona es un hilo

Se coordinan con recursos compartidos y colas; nadie conoce a los demás hilos.

“Ya pidió” = el mozo tomó el pedido

Eso decide quién se va y quién se queda cuando cierra el local.

Mozos sin mesa asignada

Una cola con prioridad: servir, después tomar pedidos, después limpiar.

Los cocineros reparten un pedido

Pedidos en orden de llegada, plato por plato. La mesa se libera recién al limpiarla.

  • Qué diseñamos: cada cliente, mozo, cocinero y cajero es un hilo (un Runnable en un pool); se coordinan con recursos compartidos y colas de mensajes.
  • Arriba, el recorrido del cliente: puerta (semáforo), sala (monitor), mesa (monitor + barrera).
  • Al medio, el circuito de trabajo: la barrera encola TOMAR_PEDIDO, el mozo lleva el pedido a la cocina, el cocinero que completa el pedido encola SERVIR.
  • A la izquierda, el pago: cola única de caja y un CompletableFuture que el cajero completa.
  • Abajo, la visualización: todos notifican a EstadoRestaurante, que encola eventos para el único hilo Display.
  • Colores del diagrama: oscuro = hilo, azul = monitor, borde negro = lock o semáforo, amarillo = cola bloqueante. Debajo de cada actor figura su pool.
  • Las cuatro tarjetas son nuestras decisiones de diseño: son interpretaciones del enunciado, no vienen dadas.

wait() / notifyAll(): siempre dentro de un while

public synchronized boolean esperarMozo() throws InterruptedException {
    ⟦while (!pedidoTomado && !cancelada)⟧ {
        wait();          // suelta el monitor mientras espera
    }
    return pedidoTomado;
}
Quién esperaCondiciónQuién notifica

Mesa.esperarComidaservidaservir
SalaDeEspera.esperarMesael grupo tiene mesa o se cerróingresar, mesaLiberada, cerrar
  • ¿Por qué while? Hay despertares espurios y notificaciones que no son para ese hilo: al despertar hay que volver a evaluar la condición.
  • ¿Por qué notifyAll? En la misma mesa esperan hilos por condiciones distintas (mozo, comida, cierre). Con notify se podría despertar al hilo equivocado.
  • Elegir el menú usa wait(timeout) en lugar de sleep: el notifyAll de cerrar() lo corta enseguida.
  • El wait libera el monitor: por eso el mozo puede entrar a tomarPedido mientras los clientes esperan.
  • Un sleep no se puede despertar sin interrumpir el hilo; el wait con timeout sí, con el notifyAll del cierre. En el código es Mesa.elegir, con TimeUnit.NANOSECONDS.timedWait(this, resta) dentro de un while.

Sincronización

Barreras: CyclicBarrier y CountDownLatch

this.barrera = new CyclicBarrier(capacidad, ⟦this::llamarMozo⟧);
private synchronized void llamarMozo() {   // la ejecuta el último
    if (cancelada) return;
    estadoMesa = EstadoMesa.ESPERANDO_MOZO;
    colaMozos.encolar(TipoTarea.TOMAR_PEDIDO, this, /* … */);
}
  • Una barrera de P partes por mesa. Nadie llama al mozo hasta que eligieron los P; la acción de barrera lo llama una sola vez.
  • Cíclica: se reutiliza con cada grupo que ocupa la mesa. Si se rompe, se cancela la ocupación y se hace reset() al limpiar.
  • CountDownLatch, dos: senalCierre (el temporizador avisa que llegó T) y empleadosTerminados (Z+C+Y: el coordinador espera a todo el personal).
“Todos eligieron: la mesa 2 llama a un mozo” → Z1 va a tomar el pedido
  • Es exactamente la regla: luego de que los P eligen, llaman al mozo. Por eso preferimos CyclicBarrier a Phaser: P es fijo.
  • En el cierre, los cancelados también atraviesan la barrera, así que nunca queda un await colgado.
  • Detalle si preguntan: esperarCompaneros() no es synchronized; si lo fuera, el primero esperaría en la barrera con el monitor tomado y los demás no podrían llegar.
  • senalCierre: el coordinador espera con await() y el generador de clientes con await(tp) en vez de sleep. empleadosTerminados: cada empleado hace countDown en su finally.

Por qué es el patrón principal

  • Desacopla: el productor no sabe quién atiende. Los mozos no tienen mesas asignadas.
  • Sin espera activa: take() bloquea sin gastar CPU (“si no hay nada que hacer, esperan”).
  • Balancea: Y cajeros sobre una sola fila.
  • Ordena: un consumidor sobre una cola FIFO, así que el Display respeta el orden real.
  • Cierre limpio: una poison pill al final de la cola.
  • Sin deadlocks: producir nunca bloquea.
  • Las colas bloqueantes son nuestra herramienta de pasaje de mensajes: los hilos no comparten estado, se pasan mensajes inmutables (TareaMozo, Pago, Evento).
  • La de mozos es de prioridad: 0 SERVIR, 1 TOMAR_PEDIDO, 2 LIMPIAR, 3 FIN; a igual prioridad, FIFO.
  • El patrón aparece en cuatro lugares; en la cocina el búfer es una lista con lock + Condition (variante de la cátedra: buffer con exclusión mutua + espera por condición).
  • Los puntos de colores son las prioridades: rojo SERVIR, amarillo TOMAR_PEDIDO, azul LIMPIAR.

Qué pasa cuando algo falla

} catch (InterruptedException e) {
    ⟦Thread.currentThread().interrupt();⟧
} finally {
    /* avisa que terminó · countDown del latch */
}
  • InterruptedException: se restaura la bandera y el hilo termina en orden.
  • finally en todo unlock(), release() y countDown(): nada queda tomado.
  • FabricaHilos pone un UncaughtExceptionHandler: lo inesperado va a la consola y al log.
  • Un error en un evento no mata al Display: lo registra y sigue.
  • Fijo para el personal porque la cantidad es conocida; cached para los clientes porque varía. El generador de clientes corre en otro newSingleThreadExecutor.
  • El Display tiene que ser un único hilo: con dos consumidores se perdería el orden.
  • FabricaHilos además les pone nombre (mozo-1) y lleva la cuenta de los hilos creados, para verificar al final que ninguno quedó vivo.
  • Si la barrera de una mesa se rompe (BrokenBarrierException), se cancela esa ocupación y la barrera se reinicia al limpiar la mesa.

Seguridad en hilos · deadlocks y visibilidad

Deadlocks y visibilidad

Sin deadlocks: no hay espera circular

  • Sin locks anidados entre recursos. Única cadena: barrera → mesa, nunca al revés.
  • Lock hoja: con el write lock de EstadoRestaurante no se toma nada más.
  • Colas ilimitadas: encolar con un monitor tomado nunca bloquea.

Visibilidad: nada se lee de la caché

  • Atómicos: abierto lo leen todos los clientes; platosPendientes, todos los cocineros.
  • volatile donde hay un escritor y varios lectores: Simulacion.resultado, Display.ultimaSecuencia.
  • Todo lo demás se toca solo con su lock: salir de un synchronized o hacer unlock() publica los cambios.
  • Leer el grafo: las flechas grises son “tomo B teniendo A”; las rojas son órdenes que evitamos a propósito.
  • Mesa → EstadoRestaurante y Mesa → ColaMozos son seguras porque esos son locks hoja o colas que no bloquean.
  • terminarLimpieza hace barrera.reset() ANTES del synchronized(this) para no invertir el orden barrera → mesa.
  • También: la carrera mozo/cierre se resuelve dentro del monitor de la mesa; no hay esperas infinitas (tryAcquire con timeout, awaitTermination con límite); contra la inanición, colas FIFO y semáforo y lock justos.
  • Visibilidad: cada dato compartido está cubierto por una relación happens-before. El detalle está en el anexo.

Terminación · visualización

Cierre en T, Display y log

  1. Se cierra la puertaabierto = false: los de afuera salen de su tryAcquire y se van.
  2. Se van los que no pidieronnotifyAll en la sala y en cada mesa: sin pedido tomado, la mesa se cancela.
  3. Los que pidieron terminanComen, pagan y salen. El personal sigue trabajando hasta que no queda nadie.
  4. Termina el personal y se apaga todoPoison pills a mozos y cajeros, cocina().cerrar(), pools apagados y log cerrado.
Para cada espera hubo que definir quién la despierta y cómo se entera el hilo de que tiene que irse.
CERRANDO · la fila de afuera se fue · M1 sigue: ya había pedido

Display y log

  • Cada cambio pasa por notificar(): aplica el cambio, saca una foto inmutable del restaurante y encola el Evento.
  • Un único hilo Display hace take() en orden y sigue hasta vaciar la cola, aun después de T.
  • Por cada evento escribe el log de texto (la acción y el estado completo), la consola y el mapa.
  • El temporizador libera senalCierre en T; el coordinador ejecuta el cierre en este orden (Simulacion.correr). Los ocho pasos con sus métodos están en el anexo.
  • La barrera nunca se traba: los P clientes de una mesa siempre llegan a ella, incluso los cancelados.
  • Display: los tres pasos de notificar() van bajo el write lock, por eso el orden de la cola es el orden real. El Display termina con una poison pill (Evento.FIN) cuando ya terminaron todos los actores.
  • El log queda en logs/simulacion-fecha.log; al final se agregan los invariantes verificados.

Introducción

Qué diseñamos

  • Cada cliente, mozo, cocinero y cajero es un hilo: un Runnable que corre en un pool de Executors.
  • Se coordinan con recursos compartidos (monitores, locks, semáforo, barreras) y colas de mensajes.
  • A los T ms el local cierra en orden: nadie queda colgado y no queda ningún hilo vivo.
  • Cada cambio genera una foto inmutable del estado, que va al log, a la consola y al mapa web en vivo (SSE).

Exclusión mutua · 1

synchronized + monitores Mesa · SalaDeEspera

  • Mesa: estado + condiciones (pedidoTomado, servida, cancelada) bajo el lock intrínseco. Clientes, mozos y el coordinador las leen y modifican.
  • SalaDeEspera: arma grupos de a P en FIFO y tiene su propia lista de mesas libres.
  • Un lock por recurso, no uno global. Un lock global sería correcto, pero serializa a todos los actores.
  • Nadie toca ese estado desde afuera: patrón Monitor.
public synchronized void servir(int mozoId) {
    servida = true;
    estadoMesa = EstadoMesa.COMIENDO;
    estado.notificar(/* … */);
    ⟦notifyAll();⟧   // despierta a los que esperan la comida
}
Grupo 5 [9, 11] completo espera mesa · la mesa 1 se está limpiando
El grupo recién consigue mesa cuando un mozo termina de limpiar y llama a sala().mesaLiberada(mesa), después de salir del monitor de la mesa.
  • Elegimos monitor para Mesa porque tiene varias condiciones sobre el mismo estado y varios tipos de hilos que esperan.
  • La sala no toca el monitor de las mesas: tiene su propia lista. Eso evita locks anidados (lo retomamos en deadlocks).

Exclusión mutua · 3

ReentrantReadWriteLock EstadoRestaurante

lock.writeLock().lock();
try {
    if (cambio != null) cambio.aplicar(vista);           // 1
    long seq = ++secuencia;
    long t = tiempoMs();
    Snapshot foto = vista.foto(seq, t, tiempoTotalMs);     // 2

Los tres pasos (1 aplicar el cambio · 2 sacar la foto · 3 encolar el evento) son atómicos: el orden de la cola es igual al orden real de los cambios, y cada evento lleva el estado del momento exacto en que se produjo.
  • Muchos escritores (cada cambio de cada actor) y lectores esporádicos (snapshotActual()).
  • Varios lectores leen a la vez sin bloquearse entre ellos.
  • Es un lock hoja: con él tomado no se toma ningún otro lock.
  • Este es el único punto de notificación del sistema: por eso el Display puede garantizar el orden.
  • El número de secuencia se asigna bajo el write lock, en el mismo paso en que se encola.

Condición de carrera resuelta en el monitor

“El mozo toma el pedido” contra “cierra el local”

public synchronized List<Eleccion> tomarPedido(/* … */) {
    if (⟦cancelada⟧) { notifyAll(); return null; }
    ⟦pedidoTomado = true;⟧
    // …
}

public synchronized void cerrar() {
    cerrando = true;
    if (⟦!pedidoTomado⟧) { ⟦cancelada = true;⟧ /* … */ }
    notifyAll();
}
Los dos métodos son synchronized sobre la misma mesa: se ejecutan uno después del otro y gana el que entra primero al monitor.

Caso A entra primero tomarPedido

  1. pedidoTomado = true
  2. cerrar() ve el pedido tomado y no cancela nada
  3. Los P clientes comen, pagan y se van

Caso B entra primero cerrar

  1. cancelada = true y notifyAll()
  2. tomarPedido devuelve null y el mozo descarta la tarea
  3. Los P clientes se van sin pedir; la mesa queda SUCIA y se limpia igual

Nunca hay un estado intermedio. Lo probamos con 25 000 carreras sobre una mesa aislada.

  • Interpretación: “realizó su pedido” significa que el mozo ya ejecutó tomarPedido.
  • No hace falta otro lock ni otra bandera atómica: el propio monitor de la mesa serializa las dos operaciones.
